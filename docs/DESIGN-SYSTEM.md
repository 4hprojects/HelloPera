# HelloPera Design System

**Source of truth for visual design:** `docs/HelloPera Finance UI Showcase.png`.
**Source of truth for brand identity:** the brand set in `image/` — see §2.

That file is the design. This document records how it is implemented, and —
more importantly — the four places the implementation deliberately departs
from it, with the measurement behind each. Read this before changing a colour
token, and re-read the showcase before building a new screen.

Implementation lives in `app/globals.css` (tokens), `components/ui/`
(primitives), `components/charts/` (SVG charts), `components/dashboard/`
(hero, stats, promo) and `components/icons/` (the line set).

## 2. Brand assets

The brand set in `image/` is the only hand-authored art in the repo. It was
replaced in September 2026: the mark changed from a smiling wallet to a **coin
purse with a peso coin**, and the wordmark gained a proper lockup.

Two files are the generation sources. The rest are reference and
platform-specific cuts.

| File | What it is | Used by the build? |
|---|---|---|
| `image/Icon-only-master.png` | 1318×1193 mark, transparent — the coin purse | **Yes** — every icon |
| `image/Primary-horizontal-logo-with-tagline.png` | 2172×724 lockup, transparent — mark + wordmark + "Your finances, organized." | **Yes** — social cards |
| `image/Primary-horizontal-logo.png` | The same lockup without the tagline | No |
| `image/Stacked-logo.png` | 1254² vertical lockup | No |
| `image/App-icon.png`, `Maskable-PWA-icon.png` | 1254² rounded tiles on a **white** field | **No — see below** |
| `image/Favicon.png` | 1254² full-bleed teal tile | No |
| `image/Monochrome-white.png`, `Monochrome-dark.png` | Single-colour lockups | No |
| `image/Marketing-lifestyle-version.png` | Annotated brand-guideline sheet | No — it is documentation, not an asset |

**Why the pre-rendered app and maskable tiles are not used.** Both are drawn as
a rounded tile on a white field. A maskable icon is cropped by the launcher to
a circle or squircle, so those white corners would appear as white arcs around
the mark. They are correct as reference art and wrong as build sources.

Everything derived from them is generated by `npm run icons`
(`scripts/build-icons.mjs`) and committed:

| Output | Source | Notes |
|---|---|---|
| `app/favicon.ico` | Icon | 16/32/48, PNG-in-ICO |
| `app/apple-icon.png` | Icon | 180², opaque — iOS composites transparency onto black |
| `app/opengraph-image.png` + `twitter-image.png` | Logo | 1200×630 on Mist, with `.alt.txt` |
| `public/icons/icon-192.png`, `icon-512.png` | Icon | `purpose: "any"`, tile transparency kept |
| `public/icons/icon-maskable-512.png` | Icon | `purpose: "maskable"`, mark at 80% on Deep Ink `#132238` |

**The maskable ground is measured, not chosen.** Against the purse body
`#027C6B`:

| Ground | Ratio | Verdict |
|---|---|---|
| `#047F6E` the mark's own mean green | 1.04:1 | invisible — the purse dissolves into its tile |
| `#02594E` the brand sheet's favicon teal | 1.61:1 | weak at 16px |
| `#132238` Deep Ink | **3.12:1** | clears WCAG 1.4.11's 3:1 for a graphical object |

Deep Ink is also an approved ground in the brand sheet's own "Dark / Ink"
favicon row, so this is the designer's option rather than a new one — and it
matches `--hp-nav`, the rail the signed-in app already uses.

Two things that are load-bearing and easy to undo by accident:

- **The maskable icon cannot be a zoomed tile.** The source tile's corner
  radius is 23% of its own width, so zooming until the curve leaves the canvas
  crops the growth arrow and the sparkles. It sits at 80% on a flat ground
  instead — `#10704C`, the mean of the tile's own outer ring, so the ring around
  it cannot read as a seam in any one direction. A blurred copy of the artwork
  was tried as a backdrop first and is worse: the coin smears into a yellow
  bloom that looks like a rendering fault.
- **The mark holds at 16px** — the tile, the gold coin and the smile all still
  read — but only just. Anything smaller needs a simplified mark, and that is
  a design task, not a resampling one.

`BRAND.themeColor` is still Primary Jade `#138A72`, which is the UI colour, not
the icon's green. The PWA splash therefore pairs a jade chrome with a green
icon. Worth a look on a real device install before launch.

## 3. Where the implementation departs, and why

### 3.1 Small coloured text uses darker variants of the same hues

The showcase paints delta and hint text in the raw brand hexes. Measured on
white:

| Showcase text | Hex | Ratio | WCAG 2.2 AA (4.5:1) |
|---|---|---|---|
| "↑ 2.5% from last month" | `#2E9B62` | 3.51 | fail |
| "↓ 8% from last month" | `#C94F5C` | 4.42 | fail |
| "3 due this month" | `#C9963E` | 2.65 | fail |
| Muted labels | `#6F7C87` | 4.28 | fail |

These are amounts and deltas — the text a finance app exists to be read for.
So each semantic colour has a `-text` variant carrying the same hue at a
readable weight, and every one is measured on **each surface it appears on**,
not just the page background:

| Token | Hex | On background | On its tint | On white |
|---|---|---|---|---|
| `--hp-primary-text` | `#107A66` | 4.91 | 4.58 | 5.25 |
| `--hp-success-text` | `#217A4B` | 4.97 | 4.68 | 5.32 |
| `--hp-warning-text` | `#96600F` | 4.93 | 4.62 | 5.28 |
| `--hp-danger-text` | `#B8404E` | 5.05 | 4.63 | 5.41 |
| `--hp-gold-text` | `#8A6413` | 5.01 | 4.70 | 5.37 |
| `--hp-text-muted` | `#647080` | 4.70 | — | 5.03 |

The brand hexes are still used exactly as drawn for **fills, borders, chart
marks, chips and illustrations** — everywhere contrast is a 3:1 graphical
requirement rather than a 4.5:1 text one.

### 3.2 Charts are SVG, server-rendered, with a table underneath

**A deliberate deviation from `PHASE-06` §36**, which says "Use a React chart
library appropriate for Next.js" and names Recharts. Measured against §36's
own four requirements:

| §36 asks for | Hand-rolled SVG | Recharts |
|---|---|---|
| Lazy-load where appropriate | No client JS at all — nothing to load | ~100KB gz behind a `'use client'` boundary |
| Avoid huge bundles | 0 KB | Would be the largest dependency in the app |
| Responsive containers | `viewBox` — correct on first paint, no JS | `ResponsiveContainer` measures after mount, so one frame of empty chart |
| Accessible summaries | A real `<table>` with every number | `role="img"` plus a description; per-datum values need rebuilding anyway |

There is a money argument too: a client chart component needs its data
serialised across the RSC boundary, and `Money` is `bigint`, which is not
JSON-serialisable. Every chart would force a bigint→float conversion in the
payload — the one thing this codebase's money discipline exists to prevent.

The single genuine loss is hover tooltips, which §37 pre-empts: "Do not make
information available only through color or hover." §73's "Production chart
bundle loads correctly" is therefore checked off as *no chart bundle exists*,
verifiable from the build output.

No chart library. The markup is complete on first paint, costs no client
bundle, and re-tints from CSS variables in both themes.

Bar charts use a **signed domain** (`signedDomain` in `lib/analytics/series.ts`):
net cash flow goes negative, and scaling |value| from a zero baseline would
draw −₱8,000 identically to +₱8,000.

Each chart pairs the graphic (`aria-hidden`) with a real `<table>` carrying
the same numbers — visually hidden for the bars, visible as the legend for the
donut. A chart with `role="img"` and a one-line summary tells a screen-reader
user the shape and withholds the data.

The donut's percentages are text in the legend, so the reading never depends
on telling six colours apart. Chart series are each ≥3:1 on the card surface
for the same reason.

### 3.3 Dark theme is a real second design, not an inversion

The showcase is light-only. Every token has a measured dark counterpart, and
two surfaces flip rather than invert:

- **The navigation rail stays dark in both themes** (`--hp-nav-*`), so its
  foregrounds are measured against the rail, never the page.
- **The hero's ridges reverse.** In light theme they darken the sky; in dark
  theme they deepen it (`--hp-hero-band`: `#138A72` → `#02120F`). Without that
  flip the ridges become *lighter* than the sky and no single text colour is
  readable across all four bands. Worst measured case for `--hp-on-hero`:
  6.27 light, 12.05 dark.
- The sand promo panel has its own `--hp-on-sand` / `--hp-on-sand-accent`.
  The accent is `#0D6857`, not `--hp-primary-text`: jade `#107A66` on sand
  `#F3E7D3` is 4.30 and fails.

### 3.4 The wordmark uses UI colours, not logo colours

The logo art and the showcase palette are not the same greens. Measured:

| | Logo art | Showcase | Δ hue |
|---|---|---|---|
| Wallet body | `#03493C` (169°) | Primary Jade `#138A72` (168°) | **1°** |
| Growth bars | `#1F9B57` (147°) | Success `#2E9B62` (149°) | **2°** |
| "Pera" wordmark | `#118836` (139°) | Primary Jade `#138A72` (168°) | 29° |
| Growth arrow | `#66E973` (126°) | Soft Jade `#45C2A5` (166°) | 40° |
| Coin | `#FCC51D` (45°) | Gold Accent `#C9963E` (38°) | 7° |
| "Hello" wordmark | `#0C2A24` (168°) | Deep Ink `#132238` (216°) | 48° |

The two largest masses of colour — the wallet body and the growth bars —
land within 2° of the showcase's Primary Jade and Success. The families
agree. What diverges is the *accent* set: the logo's wordmark and arrow are
grass green, the UI's are jade, and the logo's dark is a green-black while the
UI's is a blue-black.

`<AppLogo>` therefore renders the real wallet mark beside a wordmark in the
**UI** tokens. The showcase makes the same substitution — it draws the
"HelloPera" wordmark in its own jade — so this follows the design rather than
inventing a third position. It also matters for reading: logo grass `#118836`
is 4.57:1 on white, which only just clears AA and fails on any tinted ground.

**Open for the owner to decide:** whether the UI should move toward the logo's
grass green, or the logo's accents should move toward jade. Nothing in the
build depends on the answer — the palette is one token block.

### 3.5 Two functional differences

- **"Due soon" is amber, and so is "due today."** `statusTone()` gives both
  `warning`. They are the same "act now, nothing is late yet" state; the label
  is what separates them, and `obligation.test.ts` asserts no two statuses
  ever share both a tone and a label.
- **The top bar carries a theme toggle**, which the showcase does not. Below
  `sm` it is hidden — the bar is already search, bell and account — and the
  same control appears under Settings → Appearance, where the mobile bar's
  "More" tab lands.

## 4. Rules that are not negotiable

1. **Colour is never the only signal.** Every badge, amount and delta carries
   its meaning in text as well. Check any new component in greyscale.
2. **Amount signs come from the transaction type, not the stored number.**
   Amounts are stored unsigned (Phase 02 §73); `<Amount showSign>` derives the
   direction from the analytics class. Taking the sign from the value prints
   every expense as a gain.
3. **Measure, don't estimate.** Any new colour pairing gets a computed ratio
   recorded next to the token, against every surface it lands on.
4. **Currencies are never summed.** Per-currency figures only — master plan
   §11.

## 5. Still open

- The mark needs a simplified variant for anything under 16px; the current
  art is too detailed to reduce further.
- `BRAND.themeColor` is jade while the app icon is green — check the PWA
  splash on a real device install.
- The stat-card icon chips reuse the shared line icons; the showcase draws a
  bespoke glyph per card.
- Transaction rows use a type-coloured chip; the showcase shows per-merchant
  marks.
- "Upcoming bills" has no sparkline — there is no meaningful series behind it,
  so it carries the due count instead.
