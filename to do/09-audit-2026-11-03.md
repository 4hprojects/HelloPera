## New tasks

Severities come from code review. None was reproduced as an incident.

<a id="hp-031"></a>

### HP-031 — Bound image decoding and upload volume (P1, done on P1 branch)

- `MAX_IMAGE_DIMENSION = 12_000` (`lib/documents/validation.ts:34`) allows about 144 MP, which is roughly 0.5 GB per decode. `processImage` decodes twice (`services/image-processing.service.ts:71-87`), and OCR decodes again. `limitInputPixels` is never set, and neither is sharp's concurrency or cache.
- `prepareUploadAction` and `finalizeUploadAction` (`app/actions/documents.ts:38-91`) have no rate limit and no per-user storage quota. Staged 25 MB objects live for 24 hours.
- A draft save can create 30 records per request with no rate limit (`app/actions/extraction.ts`).
- **Acceptance:** sharp has a pixel cap and concurrency 1. Each image is decoded once. Upload actions are rate limited. A per-user storage quota is enforced. Unit tests cover all of these.
- **Decided 3 November:** 1 GB per user, 30 uploads per user per hour.

<a id="hp-032"></a>

### HP-032 — Throttle public routes that do real work (P1, done on P1 branch)

- `/api/platform-check` runs sharp on every call, unauthenticated.
- `/api/health/ready` makes two admin-client backend calls on every call, unauthenticated.
- `/api/export` builds a full export on every call, with no rate limit.
- `/api/documents/[id]/[which]` does not check `id` as a UUID, and sends no `no-store` on its 401 and 403 responses.
- **Acceptance:** each route is rate limited or gated by a secret. Route tests cover the limits.

<a id="hp-033"></a>

### HP-033 — Make recurring expected income retry-safe and atomic (P1, done on P1 branch)

- `createRecurringIncome` and the "Repeats" path of `planRepeatChange` (`app/actions/obligations.ts:177-232, 470-505`) create rules with no request id, so a double submit creates duplicate pay dates.
- "This and all later" makes separate writes with no transaction (`obligations.ts:413-414`, `services/obligation.service.ts:235-282`). It overwrites later rows the user edited, and writes no audit row.
- **Acceptance:** one audited RPC with a request id. DB tests for replay and partial failure.

<a id="hp-034"></a>

### HP-034 — Close `update_transaction` and account-edit gaps (P1, done on P1 branch)

- `update_transaction` (`20261004000700_edit_entries.sql:34-88`) changes an archived account's balance. It ignores `expected_events.actual_transaction_id` links, and does not check that the category type matches.
- `update_account_details` and `upsert_bank_details` skip the archived check.
- **Acceptance:** each case is refused, with DB tests.

<a id="hp-035"></a>

### HP-035 — Extend deletion guards to newer tables (P1, done on P1 branch)

- `loan_details` and `account_details` were created after the `reject_writes_during_deletion` loop ran, so they have no guard.
- Staged uploads under `incoming/<uid>/` bypass `reject_storage_during_deletion`.
- **Acceptance:** both are guarded. A DB test writes during a deletion and is refused.

<a id="hp-036"></a>

### HP-036 — Clear dev-only dependency advisories (P2, done on P2 branch; moderate eslint advisories accepted)

- `tinypool` (critical) and `@vitest/mocker` come in through vitest 3, and `minimatch` through typescript-eslint. The fix is the vitest 4 major.
- **Acceptance:** `npm audit` is clean and all suites pass.

<a id="hp-037"></a>

### HP-037 — Test server actions and untested services (P2, in progress: priority files covered)

- Before this branch, none of the 11 files in `app/actions/` had a test. `extraction.ts` now has one.
- 20 of the 30 services have none. `obligation.service.ts` now has a create test.
- Priority order: `obligations.ts`, `finance.ts`, `documents.ts`, then the transaction and recurring-rule services.
- The DB suite also needs cross-tenant reads of `loan_details` and `account_details` as `authenticated`.

<a id="hp-038"></a>

### HP-038 — Low-severity findings (P2, done on P2 branch)

- `sweepDocumentStorage` picks the oldest 20 documents each run, and does not mark documents whose shrink failed, so 20 bad files block it forever.
- The export snapshot leaves out `loan_details`, `account_details`, the installment columns and `borrowed_date`.
- Bank details are saved in a separate call after account creation (`services/account.service.ts:105-108`), so a failure reports an error for an account that exists.
- Loans created before `loan_details` existed update 0 rows when edited.
- APR goes through `z.coerce.number()` (`schemas/finance.schema.ts:58`).
- `discardExtractionAction` swallows the RPC error.
- The OCR model is hardcoded (`lib/ocr/claude-provider.ts:26`). Make it an `OCR_MODEL` env var.
- The last 4 digits of the bank account are copied into account names, and from there into audit logs and exports.
